# Day 25｜FP16 真的比較快嗎？模型縮小一半，我最後卻決定不用它

Day 24 我已經確認，這個 Breakout 模型做一次決策其實只需要幾毫秒。

接下來我很好奇另一件很常見的最佳化方式：**如果把 FP32 換成 FP16，會不會更快？**

直覺上很合理。

FP32 用 32 個位元保存一個浮點數，FP16 只用 16 個位元。數字變小之後，模型檔案通常會縮小，GPU 要處理的資料也比較少，所以很多深度學習工作都會使用 FP16 來加速。

但強化學習有一個地方讓我不敢只看「模型有沒有變小」。

Breakout Agent 每次都會替四個動作算分數：

- 不動；
- 發球；
- 往右；
- 往左。

這四個分數就是前面一直出現的 **Q-value**。它可以簡單理解成：

> **模型覺得現在做這個動作，之後可能有多好。**

Agent 最後只做一件事：**選分數最高的那個動作。**

所以今天真正要回答的不是「FP16 能不能把模型縮小」，而是：

> **模型變小之後，Agent 還會不會做出一樣的決定？而且它真的有比較快嗎？**

---

## 先講結果：模型真的小一半，但我還是不會用 FP16

這次結果其實很乾脆：

- ONNX 模型大小從約 **13.18 MB** 降到 **6.59 MB**，少了將近 **50%**；
- 但在 60 個完全相同的遊戲狀態中，FP16 有 **4 次選到不同動作**；
- 讓兩個版本真的去玩遊戲後，原本很小的差異會一路放大；
- 更尷尬的是，這次 FP16 **沒有比較快，反而更慢**。

所以這不是一個「犧牲一點點準確度，換到很多速度」的故事。

比較像是：

> **檔案確實變小了，但決策變了，速度也沒賺到。**

下面這張圖就是這次實際測量的結果。

## 為什麼「只差一點點」也可能選到不同動作？

FP16 最大的代價，就是能表示的數字沒有 FP32 那麼細。

例如模型原本可能算出：

```text
RIGHT = 4.8123
LEFT  = 4.8122
```

兩個分數只差一點點，但 RIGHT 還是比較高，所以 Agent 會往右。

如果換成較低精度之後，兩個數字被四捨五入成：

```text
RIGHT = 4.812
LEFT  = 4.812
```

甚至順序稍微交換，那最後選到的動作就可能不同。

這次實測正好看到了這件事。

我把同樣的 60 個遊戲狀態分別交給 FP32 和 FP16，結果如下：

| 執行方式 | 最大 Q-value 差異 | 最後動作一致率 |
| --- | ---: | ---: |
| PyTorch：FP32 vs FP16 | 0.002798 | **93.33%** |
| ONNX Runtime：FP32 vs FP16 | 0.002784 | **93.33%** |

乍看之下，`0.0028` 的差異非常小。

但重點不在小數點差多少，而是：

> **60 個狀態裡，有 4 個最後真的選到不同動作。**

其中有些狀態原本第一名和第二名的 Q-value 就非常接近，所以只需要一點點數值變化，就足以改變最後的排名。

這也是今天最重要的一個觀念：

> **對會直接做決策的模型來說，「數值很接近」不一定等於「行為一樣」。**

如果我只看平均誤差，可能會覺得 FP16 完全沒問題；但把最後動作也拿來比，問題就出現了。

---

## 4 次不同動作，真的有那麼嚴重嗎？

單看 60 個狀態，4 次不同大概就是 6.67%。

這個數字本身其實還不容易讓人感受到差別，所以我又讓 FP32 和 FP16 從相同的遊戲起點開始玩。

結果兩條路很快就分開了。

原因並不神祕：

```text
某一步選到不同動作
→ 球和板子的位置開始不同
→ 下一次看到的畫面也不同
→ 接下來的決策繼續分岔
```

最後 15 次測試裡，FP16 和 FP32 都沒有出現完全相同的最終分數與遊戲長度。

這裡有一點很重要：**這不代表 FP16 之後每四次就會錯三次。**

後面的動作一致率掉得很低，是因為遊戲早就走到不同狀態了。真正最乾淨的比較還是前面的 60 個相同畫面：同一個畫面丟進去，FP16 有 4 次做出不同選擇。

完整遊戲測試只是進一步告訴我：

> **這幾次看似很小的差異，確實有能力把後面的遊戲過程帶到不同方向。**

---

## 那至少 FP16 有比較快嗎？

這原本才是我最期待的部分。

如果 FP16 真的能明顯加速，那至少還有一個取捨問題可以討論：

> 要不要接受一點行為差異，換更快的速度？

結果這次連這個問題都不用糾結，因為 **FP16 沒有比較快。**

同一輪測試、一次處理一個遊戲狀態時：

| 執行方式 | FP32 P50 | FP16 P50 | FP32 P95 | FP16 P95 |
| --- | ---: | ---: | ---: | ---: |
| PyTorch | 7.917 ms | 9.268 ms | 8.978 ms | 10.690 ms |
| ONNX Runtime | 4.140 ms | 5.342 ms | 5.541 ms | 6.727 ms |

這裡的 **P50** 可以理解成平常最常遇到的速度；**P95** 則用來看比較慢的那一小段情況，避免只拿最好看的一次結果來比較。

這一輪裡：

- PyTorch FP16 的 P95 約慢 **19%**；
- ONNX Runtime FP16 的 P95 約慢 **21%**。

為什麼數字變小了，反而沒有更快？

因為這個模型本身不大，而且一次只處理一個狀態。真正的神經網路計算時間很短，這時候資料格式轉換、把工作交給 GPU、等待結果回來等額外成本，就可能吃掉 FP16 理論上省下來的時間。

所以：

> **FP16 比較省，不代表每一種模型、每一種使用方式都一定比較快。**

另外，Day 25 這組絕對毫秒數不拿來取代 Day 24 的正式速度基準。兩天執行時的系統狀態不同，絕對延遲有明顯變化；今天真正要比較的是**同一輪測試裡 FP32 和 FP16 誰比較快**。而這個方向很清楚：FP16 沒有得到優勢。

---

## 唯一明顯贏的地方：檔案大小

這次 FP16 最漂亮的數字其實是模型大小：

```text
FP32：13,175,034 bytes
FP16： 6,590,582 bytes
```

大約少了 **49.98%**。

如果今天最大的問題是下載大小、儲存空間或記憶體，那這會是一個很有吸引力的結果。

但對目前這個 Breakout 模型來說，我更在意的是：

1. 動作有沒有保持一致？
2. 做一次決策有沒有真的變快？

而這兩題 FP16 都沒有拿到好結果。

所以「檔案小一半」還不足以讓我採用它。

---

## 今天真正學到的，不是「FP16 不好」

FP16 當然不是一個沒用的技術。

大型模型、一次處理很多資料，或某些特別適合半精度運算的硬體與工作負載，都可能從 FP16 得到很大的收益。

但今天這個實驗讓我看到一個更實際的事情：

> **最佳化不能只看理論。**

「位元變少」可以推出模型會變小，卻不能直接推出：

```text
模型變小
= 一定更快
= 行為一定不變
```

至少在這個 Breakout 模型上，實際結果是：

```text
模型大小：✅ 小約 50%
動作一致：❌ 60 個狀態有 4 個改變
遊戲過程：❌ 很快分岔
決策速度：❌ 沒有變快
```

所以 Day 25 的答案很簡單：

> **這個模型目前不採用 FP16，繼續保留 FP32。**

這次最有價值的反而不是找到一個更快的設定，而是及早排除一個「看起來理所當然會更好，實際上卻不適合」的最佳化方向。
